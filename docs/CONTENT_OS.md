# CONTENT_OS.md — Операционная система контента

> Статус: Canon / SSoT  
> Версия: 1.0  
> Назначение: единый процесс от появления идеи до публикации, измерения и обновления.

## 1. Базовый принцип

Контент рождается из реальной работы, а не конкурирует с ней.

```text
Работа
→ наблюдение
→ тезис
→ канонический материал
→ адаптация
→ публикация
→ обратная связь
→ улучшение продукта или следующего материала
```

## 2. Источники контента

- архитектурные решения;
- изменения в продукте;
- ошибки;
- отказ от функций;
- пользовательские вопросы;
- исследования;
- реальные данные;
- интервью;
- выбор между альтернативами;
- технический долг;
- запуск и монетизация;
- работа с AI-инструментами.

Не считать достаточным источником:

- желание «что-то выложить»;
- пересказ новости;
- общий список советов;
- чужую мысль без собственного вывода;
- AI-текст без реального опыта.

## 3. Типы материалов

### Expert

Мнение, архитектурный вывод, способ мышления, анализ ошибки.

CTA на продукт не обязателен.

### Product

Конкретная проблема, сценарий, решение, результат.

CTA обязателен и ведёт только на релевантный продукт.

### Case

Структура:

1. ситуация;
2. проблема;
3. ограничения;
4. решение;
5. реализация;
6. результат;
7. что не сработало;
8. вывод.

### Research

Структура:

1. вопрос;
2. почему важен;
3. известные факты;
4. неизвестное;
5. гипотезы;
6. последствия;
7. следующий эксперимент.

### Note

Короткое наблюдение, которое может остаться внутренним или стать частью будущего материала.

### Соответствие модели сайта

Сайт поддерживает только два типа во фронтматтере — `product` и `expert` (см. TECH_SPEC.md,
CONTENT_GUIDE.md). При публикации на сайт материалы этого документа сворачиваются так:

- `Product`, `Case` → `type: product` (у `Case` используется его 8-шаговая структура как
  основа текста поста, CTA — как у любого продуктового поста);
- `Expert`, `Research` → `type: expert`;
- `Note` — черновой формат, на сайт напрямую не публикуется (либо дорастает до одного из
  типов выше, либо остаётся в `media/`).

## 5. Захват идеи

Шаблон:

```md
# Идея

Дата:
Проект:
Источник:
Наблюдение:
Почему важно:
Для кого:
Возможный формат:
Связанный продукт:
Статус: inbox
```

На этом этапе не нужно писать финальный текст.

## 6. Фильтр темы

Перед работой ответить:

1. Есть ли реальный опыт, факт или проверяемая гипотеза?
2. Для кого материал?
3. Какую одну мысль должен унести читатель?
4. Почему это должен рассказывать именно Максим?
5. Какой тип материала?
6. Какой канал канонический?
7. Стоит ли тратить время сейчас?

Отклонить материал, если:

- тема слишком общая;
- нет собственного угла;
- нет конкретной пользы;
- материал повторяет опубликованное;
- публикация нужна только ради активности;
- текст создаёт обещание, которого продукт не выполняет;
- тема уводит позиционирование в сторону.

## 7. Формулировка тезиса

До написания сформулировать:

> Этот материал показывает, что ________, потому что ________.

Если предложение не получается, материал не готов.

## 8. Доказательства

В зависимости от темы собрать:

- цифры;
- факты;
- скриншоты;
- фрагменты архитектуры;
- последовательность решений;
- пользовательскую обратную связь;
- ссылки на первичные источники;
- ограничения и альтернативы.

Нельзя придумывать отсутствующие результаты.

## 9. Каноническая версия

Сначала создаётся полная версия материала.

Канонический канал выбирается по природе темы:

- сайт — долговечный материал;
- Telegram — живое наблюдение или промежуточный вывод;
- YouTube — демонстрация и глубокое объяснение.

## 10. Адаптация

Не каждый материал публикуется везде.

### Сайт → Telegram

- оставить одну мысль;
- сократить вводные;
- добавить личный контекст;
- при необходимости сослаться на полную статью.

### Telegram → сайт

- добавить контекст;
- проверить факты;
- сделать материал независимым от текущего дня;
- структурировать;
- убрать разговорные повторы.

### Статья → видео

- не зачитывать текст;
- добавить демонстрацию;
- сократить число параллельных тезисов;
- использовать визуальные примеры.

### Статья → LinkedIn/VK

- выбрать один профессиональный тезис;
- сохранить контекст;
- не превращать в банальный список.

## 11. CTA

Допустимые CTA:

- перейти на конкретный продукт;
- прочитать полную версию;
- подписаться на основной канал;
- ответить на конкретный вопрос;
- поделиться релевантным опытом;
- связаться по конкретному поводу.

Недопустимые:

- несколько конкурирующих действий;
- давление;
- искусственная срочность;
- нерелевантная продажа;
- общий хаб вместо конкретного продукта;
- обещание гарантированного результата.

## 12. Факты, выводы, гипотезы

```md
Факт: подтверждено данными или наблюдением.
Вывод: интерпретация фактов.
Гипотеза: требует проверки.
Решение: выбранное действие с учётом ограничений.
```

## 13. Редактура

Проверить:

- один ли тезис;
- понятна ли проблема;
- есть ли доказательство;
- отделены ли факты от гипотез;
- указаны ли ограничения;
- нет ли скрытой рекламы;
- не смешаны ли продукты;
- соответствует ли текст текущему состоянию продукта;
- можно ли сократить без потери смысла.

## 14. Публикация

Фиксировать:

- ID;
- заголовок;
- тип;
- канал;
- дату;
- URL;
- связанный продукт;
- CTA;
- канонический источник;
- статус;
- результат;
- следующий шаг.

## 15. Наблюдение после публикации

Важны:

- содержательные ответы;
- вопросы целевой аудитории;
- переходы;
- регистрации;
- оплаты;
- партнёрские контакты;
- продуктовые возражения;
- новые гипотезы.

Лайки и просмотры не являются самостоятельной целью.

## 16. Обновление

Материал получает `update-needed`, если:

- изменилась цена;
- удалена функция;
- изменилась архитектура;
- ссылка не работает;
- появились новые данные;
- старый вывод оказался ошибочным.

## 17. AI в производстве

AI может:

- структурировать заметки;
- предлагать тезисы;
- находить логические разрывы;
- сокращать;
- адаптировать;
- проверять соответствие канону;
- вести реестр.

AI не может:

- придумывать опыт;
- изобретать результаты;
- автоматически публиковать без проверки;
- менять позиционирование;
- раскрывать конфиденциальные данные;
- смешивать продукты.

## 18. Безопасность

Перед публикацией удалить:

- персональные данные;
- токены и ключи;
- внутренние URL;
- IP и данные серверов;
- финансовые данные;
- чужую переписку;
- уязвимости до исправления;
- документы, не предназначенные для распространения.

## 19. Структура репозитория

`/content/posts` и `/content/pages` уже заняты сайтом (см. TECH_SPEC.md) — это то, что напрямую
рендерит Next.js, по упрощённой схеме фронтматтера (без `id`/`pillar`/`status` и т.д.). Пайплайн
этого документа живёт в отдельном каталоге `/media/`, чтобы не смешивать рабочие черновики с
опубликованным на сайте контентом:

```text
/
├── CLAUDE.md
├── docs/
│   ├── BRAND.md
│   ├── MEDIA_ARCHITECTURE.md
│   ├── CONTENT_OS.md
│   ├── CHANNELS.md
│   ├── EDITORIAL_GUIDE.md
│   └── ECOSYSTEM.md
├── content/            # сайт — canonical output для Next.js (TECH_SPEC.md)
│   ├── posts/
│   └── pages/
└── media/              # редакционный пайплайн для всех каналов
    ├── inbox/
    ├── backlog/
    ├── drafts/
    ├── canonical/
    ├── published/
    ├── archive/
    ├── research/
    ├── assets/
    └── analytics/
```

Когда материал в `media/canonical` готов и предназначен для сайта, из него собирается файл в
`content/posts/` с фронтматтером по TECH_SPEC.md — расширенные поля (`id`, `pillar`,
`canonical_channel`, `thesis`, `sensitivity` и т.д.) остаются в `media/`, на сайт не переносятся.


## 21. Критерий успеха

Система работает, если:

- идеи не теряются;
- публикации рождаются из реальной работы;
- каждый материал имеет одну цель;
- продукты не смешиваются;
- AI не размывает голос автора;
- контент создаёт накопительный актив;
- медиа не мешает разработке и бизнесу.
